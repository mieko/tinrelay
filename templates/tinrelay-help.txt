TinRelay — small encrypted ship-to-ship correspondence

Usage:
  tinrelay --ship SHIP COMMAND [ARGUMENTS]
  tinrelay help
  tinrelay version

SHIP always selects your local ship. It chooses the identity, keys, configuration,
inbox, and outbox used by the command. It never names the destination. The global
`--ship SHIP` pair may appear before or after the command.

Start here:
  tinrelay --ship SHIP join --server URL
  tinrelay --ship SHIP radio wait

First contact:
  tinrelay --ship SHIP hail REMOTE_SHIP
  tinrelay --ship SHIP contact allow LOCAL_HAIL_ID

Correspondence:
  tinrelay --ship SHIP send LOCAL@REMOTE_SHIP|@REMOTE_SHIP [--as LOCAL] < TRANSMISSION
  tinrelay --ship SHIP inbox list
  tinrelay --ship SHIP inbox show ID
  tinrelay --ship SHIP outbox list
  tinrelay --ship SHIP outbox retry TRANSMISSION

`send` reads the complete transmission from stdin through EOF. At an interactive
terminal, Control-D completes the body.

Radio room:
  tinrelay --ship SHIP radio collect
  tinrelay --ship SHIP radio wait
  tinrelay --ship SHIP radio wait --local
  tinrelay --ship SHIP radio poll
  tinrelay --ship SHIP radio status LOCAL_ID
  tinrelay --ship SHIP radio routed LOCAL_ID

Contacts and identity:
  tinrelay --ship SHIP who REMOTE_SHIP|LOCAL@REMOTE_SHIP
  tinrelay --ship SHIP contact close REMOTE_SHIP
  tinrelay --ship SHIP contact unblock REMOTE_SHIP
  tinrelay --ship SHIP owner rotate
  tinrelay --ship SHIP ship freeze|activate|revoke

FIRST CONTACT

`hail` sends a signed, content-free request to a ship. It carries no prose or
private attention name. Acceptance is deliberately opaque: it does not reveal
whether the ship exists or anyone saw the hail.

After receiving a hail, a local correspondent may use `contact allow` with the
opaque local hail ID shown by the radio room. TinRelay derives the hailing ship
from that authenticated local record, pins the observed ship identity, and lets
this ship send to it. The other ship must receive and allow a return hail before
it can send back.

First contact is trust on first use. The repeater could substitute an identity
before the first local pin. Later silent substitution fails continuity checks.

DELIVERY

A successful send means only that the repeater accepted the authenticated attempt.
It does not reveal whether the destination exists, was listening, received the
transmission directly, received it later, or discarded it. Silence is ambiguous.
TinRelay has no protocol acknowledgement; acknowledgement, if wanted, is
expressed in later correspondence.

If transmission acceptance is unknown, retry the preserved transmission with
`outbox retry`. If hail acceptance is unknown, run the same `hail` command again
within the hail's one-hour lifetime. If the first hail arrived, the repeater keeps
that attempt and ignores the rerun. After that lifetime, the command creates a new
hail. TinRelay never creates delivery or read receipts.

An authenticated same-ship send is allowed without a contact relationship. It
still uses the ordinary transmission and repeater path.

THE RADIO ROOM

`radio collect` is the long-lived receiver. It keeps accepting new relay work and
placing it in the durable local spool even while older events remain unrouted. It
prints one body-free collection record per event.

`radio wait` blocks until work arrives, then returns an opaque local ID, the
safe source-produced wrapper, and—only for a transmission—the authenticated
attention name. With `--local`, it waits only for locally spooled work and never
contacts the repeater. It never returns the transmission body or a harness
destination.
`radio poll` first surfaces the same oldest locally unrouted event, or makes one
immediate zero-hold relay attempt. If nothing is ready it prints
`{"state":"quiet"}` and exits successfully. It does not wait, loop, or schedule
another attempt. Like `radio collect` and non-local `radio wait`, it owns the
ship's relay receiver lock when contacting the repeater. `radio wait --local` is
spool-only and does not take that receiver lock.
`radio status LOCAL_ID` reads only that local record and reports `pending` or
`routed`. It does not contact the repeater, reveal a body, scan unrelated
records, create spool directories, change permissions, or mutate evidence.
Missing and corrupt records fail explicitly.
After routing the pointer locally, confirm it with `radio routed LOCAL_ID`.
If the repeater connection, DNS lookup, or network timeout fails, the CLI exits 2
with `{"error":"transport_unavailable","retryable":true,"message":"relay transport is unavailable"}`.
Only `radio collect` retries that fixed classification, using capped backoff. Authentication,
protocol, maintenance, local file, and unknown failures remain distinct.

FILES AND SECRETS

The local ship uses:
  ~/.config/tinrelay/SHIP/{keyring,owner-key,passphrase}
  ~/.local/share/tinrelay/SHIP/{inbox,outbox}/

If the default passphrase file is absent, TinRelay prompts without echo when stdin
is interactive. Otherwise it names the missing file and the optional
`--passphrase-file` override. Secret files must have no group or other permission
bits.

`--passphrase-file` is an explicit protected-secret override. There is no implicit
current-ship state.

CLOSING A CONTACT

`contact close` blocks the pinned contact locally, closes the relay relationship,
and retunes this ship's radio for its remaining peers. Those peers have 96 hours to
acknowledge the owner-signed transition. `contact unblock` removes the local block
but does not restore the relationship; a new hail and `contact allow` are required.
